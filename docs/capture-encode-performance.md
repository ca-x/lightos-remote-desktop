# 采集与编码性能记录

本次测到了本机 worker 请求打包的耗时下降，尚未测量整条远程桌面链路的 FPS、CPU
占用、端到端延迟或网络流量。浏览器继续使用原来的 WebSocket 图像格式。

## Worker 请求打包实测（2026-10-25）

同一份固定 RGBA 输入，对比原来的 `pixels.to_vec()` 加普通序列序列化，与借用
`&[u8]` 加 `serde_bytes`。两者都调用实际的 worker `pack`，生成的字节逐一相等，
仍使用协议版本 1。每个尺寸预热一次，再计时 20 次并取平均；编译结束后独立运行
三轮。下面是三轮平均值的中位数，单位毫秒：

| RGBA 输入 | 原路径 | 借用与字节序列化 | 耗时减少 | 协议字节数 |
| --- | ---: | ---: | ---: | ---: |
| 1920×1080 | 15.000 | 0.432 | 97.1% | 8,294,413 |
| 3840×2160 | 44.214 | 13.973 | 68.4% | 33,177,613 |

初测分别为 7.297 → 0.562 ms 和 28.921 → 13.947 ms，耗时减少 92.3% 和 51.8%。
全部四轮的逐轮结果约为 1080p 减少 92%～97%、4K 减少 52%～69%；
初测和复测均保存在 [原始 CSV](benchmarks/2026-10-25-worker-packing.csv)，没有丢弃较慢结果。

环境为 i5-13500H、Linux x86_64、Rust 1.99.1、release 构建；没有固定 CPU 频率或
核心亲和性，分配器与运行时负载会影响结果。这个小样本基准包括输入复制、序列化、
输出分配和释放，排除管道写入、worker 反序列化、色彩转换、GPU 编码、捕获、网络和
浏览器。协议大小完全相同，因此这些数字不能解释为带宽减少，也不能当成 FPS 提升。

复测命令：

```sh
cargo run --release --locked -p media-codec --example worker-packing
```

每帧消除了额外的 8.29 MB 或 33.18 MB RGBA 输入复制，仍然会分配二进制请求并通过
管道发送。FFmpeg 继续接收 CPU 像素，不属于 GPU 零拷贝。

## 其他优化及验证范围

- 硬件探测移到后台，首次连接只等待软件编码器的真实测试；挂起 worker 的回归用例验证软件能力在一秒内返回，硬件任务按自己的两秒测试期限退出。
- 硬件能力共用单次探测任务，失败和成功缓存分别在十分钟与一小时后允许新连接刷新；helper 或 GPU 设备身份变化使旧结果失效，身份本身不代表编码能力。
- FFmpeg 复用 RGBA/NV12 帧，写入前检查可写性；测试确认没有引用时复用缓冲，保留旧输出时内容不被覆盖。
- Portal 丢弃积压的旧捕获，只转换最新帧；转换缓冲使用两个槽和 Arc 写时复制，测试覆盖缓冲归还顺序及慢消费者的帧不可变性。
- X11 根据真实扩展能力使用 MIT-SHM 1.2 与 XDamage；静态画面跳过像素读取和全屏比较，几何查询继续刷新采集健康状态；常见 32 位通道布局直接交换字节，其他布局保留通用解码。

私有认证 Xvfb 验证了 SHM/Damage 实际启用、静态像素复用、画面变化、旧帧保留、
资源释放，以及关闭两项扩展后的 core GetImage 回退，同时保留原有输入、剪贴板和
多会话隔离验收。用例共用私有 display，因此串行执行。本机 Xvfb 没有提供测试要求的
96×72 RandR 模式，调整分辨率用例仍会明确跳过。

上述验证没有操作正在使用的桌面，也没有完成 GNOME/KDE 真机或 GPU 性能验收。
X11 静态画面的少读、Portal 缓冲复用及 FFmpeg 分配复用有行为测试，尚无整机提速
百分比。新的后端选择仍服从保存的用户选项、真实编码与解码探测、连接失败排除和
锁屏 privacy epoch；软件回退与预测帧顺序保持原有约束。
